## Question 2 - What are the backend store and artifact root used for?

The backend store is configured using:

`--backend-store-uri sqlite:///mlflow.db`

It stores structured information about MLflow experiments and runs, including:

* Experiment names
* Run IDs
* Parameters
* Metrics
* Tags
* Run start and end times
* Run status

In this lab, that information is stored inside the SQLite database file called `mlflow.db`.

The artifact location is configured using:

`--default-artifact-root ./mlruns`

It stores files generated by training runs, including:

* Trained models
* Model configuration files
* Images and graphs
* Reports
* Other output files

### What is the difference?

Metadata describes the experiment and its results. Artifacts are the actual files produced by the experiment.

**In simple terms:**

**`mlflow.db` -> searchable information about the experiments**

**`mlruns/` -> files produced by the experiments**

## Question 3 - Why should `mlflow.db` and `mlruns/` not be tracked by Git or DVC?

`mlflow.db` and `mlruns/` are generated locally whenever experiments are run.

They should not be tracked by Git because:

* They are not source code.
* They change frequently after every training run.
* Model artifacts can become very large.
* Different developers can have different local experiments.
* Tracking them would make the Git repository large and produce unnecessary changes.

They are not tracked by DVC in this lab because MLflow is already responsible for organizing experiment metadata and artifacts. DVC is being used to version the Food-11 dataset, while MLflow manages the training results.

Therefore, the following entries were added to `.gitignore`:

`mlflow.db`

`mlruns/`

**In simple terms:**

**Git -> tracks the training code**

**DVC -> tracks the dataset**

**MLflow -> tracks experiments, metrics, and trained models**

## Question 4 - What happens when `set_experiment` receives a new name?

When the following code runs:

`mlflow.set_experiment("food11")`

MLflow searches for an experiment named `food11`.

If the experiment does not exist, MLflow automatically creates it and assigns it a unique experiment ID. It then makes `food11` the active experiment.

Any runs created afterward will be stored under that experiment instead of under the `Default` experiment.

After running the script for the first time, the `food11` experiment appeared in the MLflow interface.

**In simple terms: `set_experiment` selects an existing experiment or creates it if it does not exist.**

## Question 5 - What is the difference between a parameter and a metric?

A parameter is a setting selected before training begins.

Examples include:

* Learning rate
* Batch size
* Number of epochs
* Dataset
* Model architecture

Parameters normally remain fixed throughout one run. Therefore, `mlflow.log_param` or `mlflow.log_params` records one value for each parameter and does not need a step number.

A metric is a result produced during or after training.

Examples include:

* Training loss
* Validation loss
* Validation accuracy
* Test accuracy

Metrics can change after every epoch. The `step` argument tells MLflow which epoch produced each value.

For example:

`mlflow.log_metric("val_accuracy", 0.42, step=1)`

This means the validation accuracy was 42% after epoch 1.

**In simple terms:**

**Parameter -> a choice made before training**

**Metric -> a result measured during or after training**

## Question 7 - Which learning rate gave the best validation accuracy?

The four runs produced these results:

| Run name | Learning rate | Batch size | Final validation accuracy | Test accuracy |
|---|---:|---:|---:|---:|
| `blushing-boar-71` | 0.01 | 32 | 13.69% | 12.59% |
| `receptive-robin-881` | 0.001 | 32 | 47.72% | 52.19% |
| `skillful-midge-64` | 0.0001 | 32 | **72.63%** | **75.18%** |
| `invincible-shad-365` | 0.001 | 64 | 61.22% | 66.42% |

The learning rate `0.0001` produced the highest validation accuracy: **72.63%**.

A higher learning rate was not better. The largest learning rate, `0.01`, produced the worst result because the model updates were too large and training became unstable.

**In simple terms: a learning rate that is too high can cause the model to move past good solutions instead of learning carefully.**

## Question 8 - What pattern appears in the parallel coordinates plot?

The plot shows that the run with:

* Learning rate: `0.0001`
* Batch size: `32`

produced the highest validation accuracy.

Among the two runs that used a learning rate of `0.001`, batch size `64` performed better than batch size `32`:

* Batch size `32`: 47.72% validation accuracy
* Batch size `64`: 61.22% validation accuracy

The learning rate had the clearest effect in these experiments. A learning rate of `0.01` performed very poorly, while `0.0001` performed best.

However, these four runs are not enough to prove that a smaller learning rate or larger batch size will always be better. More repeated experiments would be needed to confirm that pattern.
